**已验证的“正确模样”（拿来做验收基线）**：

- E1（源站人为 50 ms 时延）：直连源站 TTFB ≈ **51 ms**；边缘 HIT ≈ **0.5 ms**；MISS ≈ 54 ms。
- E2：副本过期后再请求 → `X-Cache: REVALIDATED`，源站 `not_modified` **+1**。
- E4：下线被选中的边缘后，再次解析 → 另一个 IP，请求仍 200。
- demo 六步：MISS → HIT（Age 增长）→ REVALIDATED → DNS 选路 → 故障切换 → 汇总。

**E5 的坑（B 必须修）**：顺序请求下“边缘吞吐低于直连源站”是正常的——因为 10 个对象 30 次请求大部分是 MISS，多了一跳。正确做法：**先预热，再只打 3 个热点对象重复请求**，此时边缘接近纯命中，吞吐差异才有意义；报告里把这个“为什么这么设计实验”写出来，本身就是加分点。

## 4. 接口冻结（10-22 10:30 前确认一次，之后只加不改）

1. `X-Cache` 只能是 `HIT / MISS / REVALIDATED`；`X-Edge` 是 `A / B`。
2. 每个服务都有 `/stats`（JSON）与 `/health`（返回 `ok`）。
3. `/stats` 字段固定：`requests, hits, misses, revalidated, evictions, bytes_from_origin, bytes_to_client, inflight, cache_entries, cache_capacity, hit_ratio`。
4. 控制端点固定：边缘 `/admin/clear`、`/admin/delay?ms=`、`/admin/capacity?n=`；源站 `/admin/max-age?seconds=`、`/admin/delay?ms=`；调度器 `/admin/edges`、`/admin/down?edge=`、`/admin/up?edge=`。
5. 端口固定：源站 `127.0.0.1:9000`；边缘 `127.0.0.1:8000`（A）/ `127.0.0.2:8000`（B）；DNS `udp 127.0.0.1:5353`；调度控制台 `127.0.0.1:8053`。

改任一条 = 群里说一声 + 同步 `docs/protocol.md`。
